## Numbers

```rust
use i18n_next::{I18n, t, tn};

let i18n = I18n::builder()
    .config("i18n.json")             // numberFormats, locales[].iso
    .formats(r#"{"en": {"short": {"notation": "compact"}}}"#)
    .build()?;
i18n.tn(1234567.891);                // "1,234,567.891" in en, "1 234 567,891" in ru
i18n.tn_as(1234.5, "currency");      // a named format of the active locale: "$1,234.50"
i18n.with_locale("ar").tn(1234.5);   // ar → ar-EG by iso: "١٬٢٣٤٫٥"
i18n.text("total").number(9.99);     // {number} in a Text, as <i18n-t :number>
t!("total", @number = 9.99);         // the same with the macro
tn!(1234.5);                         // the implicit instance (scope, else global)
i18n.language_name("de");            // Some("Deutsch"): the CLDR autonym
```

`tn(value)` takes any integer or float (`impl Into<Number>`; past 2^53 an integer is the nearest
`f64`, as JS holds it) and formats it like `new Intl.NumberFormat(tag).format(value)` with the
locale's `iso` as the tag (else its code), exactly as `@i18n-micro/core` `FormatService` does:
underscores become hyphens, a tag `Intl` does not know formats as `en`. One allocation (the
result); a `Text` with `{number}` written into a buffer allocates nothing.

Named formats are Vue I18n's `numberFormats`: `{"<locale>": {"<name>": {<Intl options>}}}`, from
`i18n.json` and `Builder::formats` (a name given again wins). `tn_as` looks the name up by the
locale code, then shorter (`zh-Hant-TW` → `zh-Hant` → `zh`); a name nowhere to be found warns (debug
builds, or `tracing`) and formats with the defaults, as JS does.

Formats are computed by an own engine on CLDR 48 data, the same CLDR as Node's ICU, and checked
against `Intl` output: the shortest decimal digits of the `f64` rounded half-expand as a decimal
(`1.005` → `1.01`), the locale's pattern, grouping (`minimumGroupingDigits`, Indian `12,34,567`),
default numbering system and currency spacing. The few places where ICU formats differently from the
CLDR JSON (currency patterns of English in Europe, `fr-CH` separators, the layout of `currencyDisplay:
name`, the currency names of `sr-Cyrl-ME`) are read back from ICU when the data is generated.

| `Intl.NumberFormat` option | v1 |
| --- | --- |
| `style: decimal`, `minimumFractionDigits`, `maximumFractionDigits`, `minimumIntegerDigits` | yes |
| `useGrouping`: `true` / `false` / `"always"` / `"auto"` / `"min2"` | yes |
| `style: percent` | yes |
| `style: currency` + `currency`, `currencyDisplay: symbol / narrowSymbol / code` | yes |
| `currencyDisplay: name` | with the `currency-names` feature (the number as ICU shows it there: `€1,234.50 euros` in `en-150`, `US$1,234.50 US dollars` in `en-DE`) |
| `notation: compact` (`compactDisplay: short`), with `style: decimal` | yes |
| default numbering system of the locale (`ar-EG` → `١٬٢٣٤`); `numberingSystem` naming it | yes |
| `style: unit`, `signDisplay` other than `auto`, `roundingMode`, significant digits, `notation: scientific / engineering`, `compactDisplay: long` with compact, compact currency or percent, another `numberingSystem` | no: `Error::UnsupportedFormat` at `build()` |

Options at their default value (`notation: "standard"`, `signDisplay: "auto"`, `currencySign:
"standard"`, `numberingSystem` of the format's locale…) are accepted, unknown keys are ignored (as by
`Intl`), and values `Intl` throws on (`currency: "usdx"`, `minimumFractionDigits` over
`maximumFractionDigits`) are errors too. Values are read as `Intl` reads them: digits by `ToNumber`
(`"2"`, `"0x2"`, `null` → 0, `true` → 1, `[2]`), strings by `ToString`, `useGrouping` falsy (`0`, `""`,
`null`) is off, a key given twice takes its last value. A `-u-nu-` extension in a tag is not read.
Known differences (`fixtures/compat/README.md`): `en-US-POSIX` formats as `en-US` (ICU: no grouping),
and ICU's misplaced name where currency spacing meets a symbol of letters in `currencyDisplay: name`
(`CHF 1,234.5 Swiss francs0` in `en-DE`) is written as `CHF 1,234.50 Swiss francs`.

## Dates and relative time

```rust
use i18n_next::{I18n, RelativeOptions, t, td, tdr};

let i18n = I18n::builder()
    .config("i18n.json")                          // datetimeFormats, locales[].iso
    .datetime_formats(r#"{"en": {"long": {"dateStyle": "full", "timeStyle": "short"}}}"#)
    .time_zone("Europe/Berlin")                    // default: the system zone
    .build()?;
let at = 1_704_428_640_000i64;                     // ms since 1970, as a JS Date holds it
i18n.td(at);                                       // "1/5/2024"; ru "05.01.2024"; ar-EG "٥‏/١‏/٢٠٢٤"
i18n.td_as(at, "long");                            // "Friday, January 5, 2024 at 5:24 AM"
i18n.tdr(at - 3 * 86_400_000);                     // "3 days ago" (now: the clock)
i18n.tdr_with(at - 86_400_000, RelativeOptions::default().auto());  // "yesterday"
i18n.text("due").date(at);                         // {date} in a Text, as <i18n-t :date>
t!("seen", @relative = at);                        // {relativeDate}, as <i18n-t :relative-date>
td!(at); td!(at, "long"); tdr!(at);                // the implicit instance (scope, else global)
```

`td` takes an `impl Into<Timestamp>`: milliseconds as `i64` or `f64` (truncated, `NaN` invalid, as `new
Date(ms)`), or a `SystemTime` (not on `wasm32-unknown-unknown`). A value JS cannot hold (`NaN`, past ±8.64e15
ms) shows `Invalid Date`, as `FormatService.formatDate`. Without options `td` is `new Intl.DateTimeFormat(tag)`:
year, month and day, numeric, in the instance zone. `tdr` is `FormatService.formatRelativeTime`: the largest unit
that fits at least once (a year is 365 days, a month 30, no weeks), rounded down, `0 seconds ago` under a second
in the past. One allocation (the result); a `Text` with `{date}` or `{relativeDate}` written into a buffer
allocates nothing. JS checks `number`, `date`, `relativeDate` in that order: a `Text` fills one of them.

Named formats are Vue I18n's `datetimeFormats`, looked up like number formats (`zh-Hant-TW` → `zh-Hant` →
`zh`); a name nowhere to be found formats with the defaults and warns. A format's own `timeZone` wins over the
instance's.

How it matches `Intl` (spikes S9 / S10): ICU's pattern of every supported option combination (215 date ×
26 time combinations, five hour cycles, the styles and the glue that joins a date and a time) was taken from
Node's ICU when the data was generated (`formatToParts` on probe dates: single-digit days and hours fix the
widths, all months and weekdays fix width and context, `мая` against `май`), checked there by re-rendering
against `format()`, and is only rendered here. U+202F of ICU is a space, as in V8's `format()` (WebKit may
show U+202F). The month and weekday names, day periods (flexible ones for `zh-Hant`), eras and relative-time
patterns are CLDR 48 as ICU has it.

| `Intl.DateTimeFormat` / `RelativeTimeFormat` option | v1 |
| --- | --- |
| `dateStyle` (`full` … `short`), `timeStyle` (`medium`, `short`), both together | yes |
| `weekday`, `year`, `month`, `day`, `hour`, `minute`, `second`, any combination | yes |
| `hour12`, `hourCycle` (`h11`, `h12`, `h23`, `h24`) | yes |
| `timeZone` (IANA) | yes; UTC only without the `tz` feature |
| `calendar: "gregory"`, `numberingSystem` naming the locale's, `localeMatcher`, `formatMatcher` | yes |
| relative `numeric: always / auto`, `style: long / short / narrow` (`RelativeOptions`) | yes |
| `timeStyle: full / long`, `timeZoneName` (zone names), `era`, `dayPeriod`, `fractionalSecondDigits`, other calendars | no: `Error::UnsupportedFormat` at `build()` |

Values `Intl` throws on (`month: "numerical"`, `dateStyle` with a component, an unknown `timeZone`) fail the
build the same way; `Builder::time_zone` with an unknown zone fails with `Error::UnknownTimeZone`.

Dates are Gregorian. Five locales show another calendar in ICU by default (`th`: Buddhist; `fa`, `fa-AF`,
`ps`: Persian; `shn-TH`: Buddhist): give them `-u-ca-gregory` in their `iso` (`th-u-ca-gregory`) and both sides
show Gregorian dates; without it the front end shows its calendar and Rust the Gregorian date. `-u-hc-` and
`-u-nu-` in a tag are not read. Week years (`Y`) of the few locales whose CLDR patterns use them (`gd`, `ksh`,
`sc`) are ISO week years, as there.

## Time zones and the clock

```rust
I18n::builder().time_zone("Europe/Berlin").clock(|| now_ms).build()?;
```

The zone is `time_zone` when set, else the system's: `TZ`, then `/etc/localtime` (unix, macOS, iOS, WASI),
`Intl` in the browser; UTC when nothing says (Windows without `TZ`: see [Desktop](/platforms/desktop#time-zones)).
`set_system_time_zone(name)` gives the system zone by name once, before the first date; the Tauri plugin passes
the WebView's zone this way. Named zones come from the TZif files of the OS, the Android tzdata, the bundled
tzdb (Windows, feature `tzdb`) or `Intl` in the browser. `clock` is "now"
for `tdr` in milliseconds (JS `FormatService({ now })`): pin it in tests, or hand the client the server's time so
hydration renders one text. By default `SystemTime`; in the browser `Date.now()` (feature `tz`; without it set
a clock, `tdr` shows `Invalid Date`).

## CLDR data and `I18N_NEXT_LOCALES`

The number and date data are Rust statics generated at build time (no decoder at run time; the linker drops
what an app never calls). `build.rs` takes the locales of the environment variable
`I18N_NEXT_LOCALES` with their CLDR parent chains (`de-CH` brings `de`), plus `en` (where an unknown
tag goes) and the root:

```sh
I18N_NEXT_LOCALES=en,de,ru cargo build --release   # three locales and their parents
I18N_NEXT_LOCALES=all cargo build --release        # every locale ICU has (638)
cargo build --release                              # unset or `modern`: the 425 CLDR `modern` locales
```

A tag in the list is matched like a tag at run time, aliases included (`zh-TW` is `zh-Hant`, `de-XX` is
`de`, `iw` is `he`, `sh` is `sr-Latn`); one with no data fails the build. Only the locales ICU itself has
count: a CLDR locale ICU formats as another (`az-Arab` as `az`, `be-tarask` as `be`) is left out, and a
region ICU aliases onto a script it lacks formats with the root, as in ICU (`ku-IQ`). A locale left out formats as its nearest selected parent, else `en`.
Regional variants keep only what differs from their parent, strings are interned, patterns are parsed
in `build.rs`.

`.wasm` bytes after `wasm-bindgen` and `wasm-opt -Oz`, net of the std runtime (the size probe of the CI `size`
job: catalog, `t`, `Text`, `tn` decimal, currency and compact, `td` by default and by a named format with a zone of
its own, `tdr` and a `Text` with `{date}`):

| `I18N_NEXT_LOCALES` | Locales | Full build |
| --- | --- | --- |
| `en,ru,de` | 3 (+ parents) | 265.9 KB |
| `en,de,fr,es,ru,ja,zh,ar,pt,hi` | 10 | 306.9 KB |
| unset or `modern` (the default) | 425 | 884.3 KB |
| `all` | 638 | 1301.7 KB |

Dates add about 60 KB for three locales: some 25 KB of data (patterns of every combination, names,
relative-time patterns, the combinations ICU joins its own way) and 35 KB of code (the renderer, the options, the
zones of `tz` with their `js-sys` glue in the browser). Then about 1.4 KB per further locale: pick the locales
of a browser build with `I18N_NEXT_LOCALES`. An app that never formats a date links none of it: the date code is reached only through `td`, `tdr`, `Text::date`,
`Arg::date` and the builder calls that bring date formats or a zone (`datetime_formats`, `time_zone`,
`config`). Patterns, names and relative-time parts are interned across locales; a locale's date and time
patterns, names and overrides are shared rows (a regional variant mostly reuses its parent's).

`currency-names` (off by default) adds the plural display names of every currency for
`currencyDisplay: name`: about 1.7 MB of statics for the `modern` set (1 MB of text, 40 700 entries),
so pick the locales with `I18N_NEXT_LOCALES` when you turn it on.
