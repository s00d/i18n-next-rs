```rust [src-tauri/src/lib.rs]
use tauri_plugin_i18n_next::ManagerExt;

macro_rules! file {
    ($path:literal) => { ($path, &include_bytes!(concat!("../../locales/", $path))[..]) };
}

let i18n = i18n_next::I18n::builder()
    .config_json(include_str!("../../i18n.json"))      // embedded: works in a bundle
    .files([file!("en.json"), file!("ru.json"), file!("pages/tray/en.json"), file!("pages/tray/ru.json")])
    .missing(tauri_plugin_i18n_next::missing)   // Rust misses into the dev report
    .build()?;

tauri::Builder::default()
    .plugin(tauri_plugin_i18n_next::Builder::new(i18n).build())
    .setup(|app| {
        let quit = tauri::menu::MenuItem::new(app, "Quit", true, None::<&str>)?;
        let i18n = app.i18n();                             // derefs to I18n
        i18n.bind(&quit, i18n.page("tray").text("quit"));  // relabeled on every switch
        println!("{}", i18n_next::t!("menu.quit"));        // the plugin installed the catalog
        Ok(())
    })
```

At start the plugin installs the catalog as the global instance (`t!` everywhere; skipped when one is installed
already), applies the saved locale, registers the `i18n-next://` protocol and, in debug builds, watches the
`dir` / `lazy_dir` files and collects missing keys. `app.i18n()` returns the plugin's `Handle`, which derefs to
`I18n`; `app.state::<I18n>()` works too.

The catalog is embedded with `files` (as `examples/tauri-app` does), so a bundle started from Finder or Explorer
finds it. `dir("locales")` with a relative path resolves against the working directory: use it in development
(the watcher reloads its files), not in a release bundle ([Desktop](/platforms/desktop#shipping-the-locales)).

`examples/tauri-app` is a full app: Vue + vue-router, a native menu and tray bound to the catalog, two windows and a
command that returns a `Text`.

## Builder options

| Option | Default | Effect |
| --- | --- | --- |
| `system_locale(bool)` | `true` | the first start picks the best of the WebView's `navigator.languages` |
| `persist(bool)` | `true` | saves the active locale to `i18n-next.json` in the app config dir and applies it at the next start, if still available |
| `global(bool)` | `true` | installs the catalog for `t!` / `Text` without an instance |
| `watch(bool)` | `true` | debug builds: reloads on changes of `dir` / `lazy_dir` files; windows get `changed`, bound labels update. Release builds never watch |
| `data_dir(path)` | app config / data dir | where `i18n-next.json` and the dev `i18n-missing.json` go |
| `origins(iter)` | none | more origins the protocol answers, see [Origins](#origins) |

## Start locale

1. the saved locale (`persist`), if the catalog still has it and it is not disabled;
2. else the WebView's `navigator.languages`, negotiated against the enabled locales (`system_locale`), sent with
   the first `meta` / `load`;
3. else the catalog's start locale (`Builder::locale`, else `defaultLocale` of `i18n.json`).

The first `meta` also carries the WebView's time zone: Rust shows dates in it unless the catalog has its own
`Builder::time_zone`, and the front end formats dates in the zone the meta names, so both sides print the same.

## Protocol

The front end gets whole chunks and resolves keys itself: there is no IPC per key.

| Request | Answer |
| --- | --- |
| `GET /{tag}/{locale}/{page}.json` | one chunk (`index` is the root): `{"data":{…},"linked":{…}}` |
| `GET /{tag}/bundle?locale=…&page=…` | the roots of the locale's chain and, with `page`, its page chunks |

`{tag}` is the content tag of what the URL serves (16 hex digits); the `meta` command lists the current tags.
A change that leaves a chunk as it was keeps its URL, so `en → de → en` reads `en` from the cache. Responses are
`application/json` with `ETag` and `Cache-Control: immutable`. A request with an old tag gets `410 Gone` with the
current tag and version (body and `X-I18n-Tag` / `X-I18n-Version`), never stale data under a new URL; the front end
reads `meta` again.

The front end builds URLs with `convertFileSrc(path, 'i18n-next')`: `i18n-next://localhost/…` on macOS, iOS and
Linux, `http://i18n-next.localhost/…` on Windows and Android.

## IPC commands

| Command | For |
| --- | --- |
| `meta` | version, locale, locales, fallback chains, named formats, the tags of the active chain |
| `load`, `load_page` | the same chunks as raw bytes: the fallback when the protocol is unavailable |
| `set_locale`, `get_locale`, `available_locales`, `pages` | control |
| `report_missing` | dev builds only: front-end misses into the report |

Arguments and return types: [Commands](/reference/commands). The JS package wraps them; you rarely call them.

## Transport

Why a protocol for data and commands for control: measured on macOS (WKWebView, Tauri 2.12, release, median),
moving one payload to JS:

| Method | 81 KB | 832 KB | 8.5 MB |
| --- | --- | --- | --- |
| custom protocol `fetch().json()` | **0.35 ms** | **2.45 ms** | **21.0 ms** |
| raw invoke + `TextDecoder` + `JSON.parse` | 0.65 | 3.05 | 24.5 |
| invoke with `serde_json::Value` | 0.65 | 4.15 | 43.0 |
| `Channel` in 256 KB chunks | 0.95 | 3.55 | 29.5 |
| `JSON.parse` of a string already in JS | 0.10 | 1.25 | 17.0 |

70–85% of the time is `JSON.parse`, so the lever is how much is sent (the active chain, pages on demand,
`maxPages`), not how. More numbers: [Performance](/performance).

## Events

| Event | Payload | When |
| --- | --- | --- |
| `i18n-next://changed` (`EVENT_CHANGED`) | `{ locale, version }` | after a locale switch, `add_messages`, `reload`, a `watch` reload; in version order |
| `i18n-next://missing` (`EVENT_MISSING`) | `{ locale, page, key, count }` | dev: a key missed for the first time |

## Windows and locale

`set_locale` from JS (`link.setLocale`) or Rust (`app.i18n().set_locale`) switches Rust, every bound label and every
window: each window gets `changed` and loads its root and current page in the new locale. A change older than
one already handled is dropped, in Rust and in each window.

## Native UI: `bind`

```rust
let i18n = app.i18n();
let id = i18n.bind(&window, i18n.text("window.title"));
i18n.bind(&tray_icon, i18n.page("tray").text("tooltip"));   // feature `tray-icon`
i18n.unbind(id);
```

`bind` shows the text now and again after every change, until `unbind`. Targets: `MenuItem`, `CheckMenuItem`,
`IconMenuItem`, `Submenu`, `Window`, `WebviewWindow`, the tray icon's tooltip (plugin feature `tray-icon`), or your
own type through the `Relabel` trait. Only labels whose text changed are set. A target that fails to relabel (a
destroyed item) is unbound; a window's bindings go when the window is destroyed.

A command can return a `Text`: it is serialized as the string shown in the active locale.

```rust
#[tauri::command]
fn greeting(app: tauri::AppHandle, name: String) -> i18n_next::Text {
    app.i18n().text("greeting").arg("name", name)
}
```

## Missing keys in dev

In a debug build the plugin collects misses from the frontend (`report_missing`, sent by the JS package batched per
microtask) and from Rust (when the catalog is built with `.missing(tauri_plugin_i18n_next::missing)`: the handler
is set on the catalog, before the plugin exists). They are deduplicated by `(locale, page, key)` with a count,
written to `i18n-missing.json` in the app data dir and announced with `i18n-next://missing`, once per new key. At
most 10 000 keys of up to 512 bytes are kept. In release builds the command is not registered and the handler does
nothing; the JS package stops sending after the first refusal.

## Permissions

`i18n-next:default` allows `meta`, `load`, `load_page`, `get_locale`, `available_locales`, `pages` and
`set_locale`. `report_missing` is not in it: add `i18n-next:allow-report-missing` to a dev capability. The full
list: [Permissions](/reference/permissions).

## Content Security Policy

With `app.security.csp` set, the WebView must be allowed to fetch the protocol. Add both spellings (the second is
what Windows and Android use) next to Tauri's IPC:

```json [src-tauri/tauri.conf.json]
{
  "app": {
    "security": {
      "csp": {
        "default-src": "'self'",
        "connect-src": "ipc: http://ipc.localhost i18n-next: http://i18n-next.localhost"
      }
    }
  }
}
```

Without it the fetch is blocked and the front end falls back to raw `load`: it still works, a little slower and
without the HTTP cache. A Rust frontend (wasm) also needs `'wasm-unsafe-eval'` in `script-src`.

## Origins

Custom protocols have no ACL, so the handler checks the request: only `GET` / `HEAD` (and the CORS preflight), only
names the catalog knows (`404` otherwise; a page or locale name is never turned into a path), and only allowed
origins (`403` for any other `Origin`; a request without one passes). Allowed are the app's own
(`tauri://localhost`, `http(s)://tauri.localhost`) and, in debug builds, the dev server's. Pages served from
elsewhere that read translations need `origins`:

```rust
tauri_plugin_i18n_next::Builder::new(i18n)
    .origins(["http://localhost:1430"])   // tauri-plugin-localhost, an external URL, an Android dev host
    .build()
```

An origin is scheme, host and port as the WebView sends it, no path.
